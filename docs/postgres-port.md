# PostgreSQL port: schema, data copy, and what the data layer changed

The application runs on PostgreSQL 16 only; `DATABASE_URL` is required and
nothing at runtime uses SQLite. This document records the PostgreSQL schema
and how it is generated and checked, how to move an existing SQLite database
across (section 7), and the SQLite-specific SQL the port rewrote (section 9).
The data layer itself is described in `docs/postgres-data-layer.md`.

| File | What it is |
|---|---|
| `migrations/postgres/baseline.sql` | PostgreSQL 16 translation of `migrations/baseline.sql`. Idempotent: running it twice is a no-op the second time. Generated; do not edit by hand. |
| `scripts/postgres/generate-baseline.js` | Generates `migrations/postgres/baseline.sql` from `migrations/baseline.sql`. `--check` reports whether the committed file is current. |
| `scripts/postgres/compare-catalog.js` | Compares the PostgreSQL catalog with the SQLite schema and type-checks every trigger condition. |
| `scripts/postgres/compare-rows.js` | Compares a copied database with its SQLite source row by row. |
| `scripts/postgres/boot-parity.js` | Gate A: boots the SQLite app and the PostgreSQL `db.js` on empty databases and checks they hold the same rows after one and two boots, and that a third boot changes nothing. |
| `scripts/postgres/trigger-parity.js` | Runs the same statements against both databases and compares trigger outcomes and helper functions. |
| `scripts/sqlite-to-postgres.js` | Copies an existing SQLite database into PostgreSQL and verifies it. |
| `docs/postgres-port.md` | This document. |

`migrations/baseline.sql` remains the source of truth. After a schema change
there, regenerate and re-validate the PostgreSQL baseline (section 10).
Migration `083_gap_report_and_closure_decisions` is already folded into both
baselines; a forward migration that is not folded into `migrations/baseline.sql`
needs its own PostgreSQL migration.

## 1. Creating the database and applying the schema

```sh
createdb --template=template0 --encoding=UTF8 --lc-collate=C --lc-ctype=C isms
psql -v ON_ERROR_STOP=1 -d isms -f migrations/postgres/baseline.sql
```

**Create the database with `LC_COLLATE` and `LC_CTYPE` set to `C`.** SQLite
compares and sorts text byte by byte, and its `lower()`, `upper()` and `LIKE`
fold ASCII letters only. A `C` database behaves the same way; a database in a
language locale such as `en_US.utf8` does not (checked on 16.4):

| Expression | SQLite | PG, `C` | PG, `en_US.utf8` |
|---|---|---|---|
| `lower('ÄBc')` | `Äbc` | `Äbc` | `äbc` |
| `'Äb' LIKE/ILIKE 'äb'` | false | false | true |
| `'a' < 'B'` (and so `ORDER BY`) | false | false | true |

The schema works under either locale, and every check below passed under
both. The copy tool prints a note when the target database is not `C`.

Settings the app's connection pool should apply on every connection:

- `TimeZone=UTC` (for example `options: '-c TimeZone=UTC'` in the pg `Pool`
  config), so `current_date` and `now()::date` mean the UTC day, as SQLite's
  `date('now')` does.
- Type parsers: node-pg returns `bigint` (every id and every `count(*)`) and
  `numeric` (`sum()` of a bigint, `avg()`) as **strings**. Without
  `types.setTypeParser(20, Number)` and `types.setTypeParser(1700, Number)`,
  comparisons such as `row.id === req.user.id` quietly become false. Ids stay
  well below 2^53, so `Number` is safe.

## 2. Type mapping

| SQLite | PostgreSQL | Notes |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | 206 tables. |
| `id INTEGER PRIMARY KEY` (rowid alias, no AUTOINCREMENT) | same identity | `audit_chain` only: `db.js` inserts it without an id. |
| other single-column `INTEGER PRIMARY KEY` | `bigint PRIMARY KEY` | 6 columns that are really foreign keys (`onboarding_progress.workspace_id`, `firm_email_settings.firm_id`, `tenant_onboarding.firm_id`, `experience_rollouts.firm_id`, `experience_workspace_overrides.workspace_id`, `supplier_finding_links.finding_id`). The app always supplies them. |
| `INTEGER` | `bigint` | SQLite integers are 64-bit, and identity ids are `bigint`, so every integer column (foreign keys included) is `bigint`. 0/1 flags stay integers, not `boolean`, so `active = 1` keeps working. |
| `TEXT` | `text` | JSON columns stay `text`. |
| `DATE`, `DATETIME` | `text` | The same `'YYYY-MM-DD'` / `'YYYY-MM-DD HH:MM:SS'` strings, so slicing and string comparison in the app behave the same. |
| `REAL` | `double precision` | `real` in PostgreSQL is 4-byte; do not use it. |
| `BLOB` | `bytea` | |
| `DEFAULT CURRENT_TIMESTAMP`, `DEFAULT (datetime('now'))` | `DEFAULT utc_now_text()` | 222 columns. One helper, defined at the top of the baseline. |
| `DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))` | `to_char(statement_timestamp() AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')` | `form_drafts.saved_at` only. |

`utc_now_text()` returns `to_char(statement_timestamp() AT TIME ZONE 'UTC',
'YYYY-MM-DD HH24:MI:SS')`. It uses `statement_timestamp()`, not `now()`:
SQLite evaluates `'now'` once per statement, while `now()` is frozen for the
whole transaction.

Kept exactly as declared: every `CHECK` (409), `UNIQUE` constraint (157),
primary key (225), partial index, and foreign key (563) with its
`ON DELETE` action. The two `DEFERRABLE INITIALLY DEFERRED` keys on
`nonconformity_evidence_links` are also kept.

Differences PostgreSQL imposes:

- **Foreign keys are created after all tables and indexes**, as named
  constraints `<table>_<columns>_fkey`, each guarded by an existence check.
  The schema has reference cycles (`generated_docs` and `doc_versions`;
  `tprm_assessment_cycles`, `tprm_client_decisions` and
  `tprm_recommendations`), and PostgreSQL checks the referenced table when
  the constraint is created.
- **`access_review_items."current_role"`** is a reserved word in PostgreSQL,
  so it is quoted in the schema. Every query must quote it too. Unquoted,
  `SELECT current_role FROM access_review_items` raises no error: it returns
  the database session's role name on every row.
- **Primary-key columns are `NOT NULL`.** SQLite allowed NULL in non-integer
  primary keys; the copy tool fails if a row has one.
- **COLLATE NOCASE:** neither the schema nor the app code uses it. If
  case-insensitive matching is needed later, use `lower(col) = lower($1)`
  with an expression index on `lower(col)`. Not `citext`: it needs an
  extension, it changes every comparison on the column, and `lower()` is
  what SQLite's own `NOCASE` does (ASCII-only in a `C` database).
- B-tree index entries are limited to about 2.7 kB. Every indexed text column
  holds keys, hashes, dates or names, so this should not bite, but a very
  long `name` would now fail to insert instead of being indexed.

## 3. Expression translation (CHECKs, indexes, views, triggers)

| SQLite | PostgreSQL | Why |
|---|---|---|
| `x GLOB 'pat'` / `NOT GLOB` | `x ~ '^regex$'` / `!~` | `*` → `.*`, `?` → `.`, `[...]` kept; anchored. `'*[^0-9a-f]*'` → `'[^0-9a-f]'`, `'????-??-??'` → `'^....-..-..$'`. Case-sensitive in both. |
| `x LIKE 'p%'` | `x ILIKE 'p%'` | SQLite's `LIKE` ignores ASCII case (the `secret_reference` CHECK). |
| `a IS b` / `a IS NOT b` (non-NULL `b`) | `a IS NOT DISTINCT FROM b` / `a IS DISTINCT FROM b` | NULL-safe comparison. Every hash-chain trigger depends on it: the first event's NULL predecessor must equal the empty history. |
| `json_valid(x)` | `x IS JSON` | PostgreSQL 16 SQL/JSON predicate. |
| `json_type(x) = 'array'` | `x IS JSON ARRAY` | |
| `json_extract(doc, '$.k')` | `(doc::json ->> 'k')` | Text for strings, the JSON text for arrays/objects, NULL for JSON null or a missing key. A JSON number or boolean comes back as text (`'1'`, `'true'`) where SQLite returns 1. The view's keys hold only strings, arrays and nulls today. |
| `json_tree(doc)` (keys) | `sqlite_json_tree_keys(doc)` | Helper returning every key at every depth, as `json_tree` does. |
| `strftime('%Y-%m-%d', x \|\| ' 00:00:00', '+0 days')` | `sqlite_date_ymd(x)` | Helper with SQLite's exact result: NULL for a bad month/day, the rolled-over date for `2024-02-30` (→ `2024-03-01`), so `= x` holds only for real calendar dates. |
| `datetime('now')`, `CURRENT_TIMESTAMP` | `utc_now_text()` | |
| `instr(a, b)`, `char(92)` | `strpos(a, b)`, `chr(92)` | |
| `typeof(embedding) = 'blob' AND length(embedding) = 8192` | `embedding IS NOT NULL AND octet_length(embedding) = 8192` | A `bytea` column can only hold bytes. |
| `(a IS NOT NULL) + (b IS NOT NULL) = 1` | `(a IS NOT NULL)::int + (b IS NOT NULL)::int = 1` | SQLite booleans are integers. |

`sqlite_date_ymd` was compared with SQLite's `strftime` on 3,241 inputs (every
month 00–13 and day 00–32 for seven years, plus malformed strings) with no
differences; `sqlite_json_tree_keys` against `json_tree` on nested documents;
`IS JSON` against `json_valid` on 18 valid and invalid inputs.

## 4. Triggers

All 189 SQLite triggers exist in PostgreSQL with the same name, table,
timing, event, `UPDATE OF` column list and condition, all `FOR EACH ROW`.

| Shape | Count | PostgreSQL form |
|---|---|---|
| `SELECT RAISE(ABORT, msg)` with no condition or a condition without a subquery | 130 | The condition stays in the trigger's `WHEN`; the shared function `sqlite_raise_abort()` raises the message passed as the trigger argument. |
| `RAISE(ABORT, msg)` whose `WHEN` has a subquery | 55 | PostgreSQL forbids subqueries in a trigger `WHEN`, so the condition moves into a dedicated `<trigger>_fn()` as `IF ... THEN RAISE ... END IF`. |
| AFTER trigger whose body re-UPDATEs the row that fired it | 3 | Now a BEFORE trigger that assigns `NEW` (`control_record_version`, `client_request_release_on_insert`, `client_request_release_on_assignment`). The stored values are the same, without a second row version or a self-firing trigger. |
| AFTER trigger updating another table | 1 | `trg_evidence_ai_source_stale` keeps its `WHEN` and runs the translated `UPDATE` in `trg_evidence_ai_source_stale_fn()`. |

**Error contract.** The message text is exactly SQLite's, and the error's
SQLSTATE is `23000` (`integrity_constraint_violation`). SQLite reports these
as `SQLITE_CONSTRAINT_TRIGGER`, so the five app sites that test
`code.startsWith('SQLITE_CONSTRAINT')` become `code.startsWith('23')`, which
also covers unique (23505), foreign key (23503), check (23514) and not-null
(23502) violations. CHECK, unique and foreign-key messages are PostgreSQL's
own wording, not SQLite's. There is no `SQLITE_BUSY` equivalent: lock waits
block, and the errors to retry are `40001` (serialization failure) and
`40P01` (deadlock).

**Firing order.** When one statement violates two guards on the same table
and event, SQLite reports the most recently created trigger and PostgreSQL
the alphabetically first. A statement that violates one guard gets the same
message in both. Example from the checks below: setting `tprm_modules` back
to `needs_classification` with a NULL `service_model` fails in both, with
`invalid TPRM module status transition` in SQLite and
`TPRM service model is immutable after classification` in PostgreSQL. Keeping
the names was preferred over renaming triggers to force an order. The
tables where this can happen (SQLite order shown):

**An error ends the PostgreSQL transaction.** SQLite's `RAISE(ABORT)` undoes
only the failing statement and the transaction carries on. In PostgreSQL every
later statement fails until `ROLLBACK`. Code that catches a constraint error
and keeps using the same transaction needs a `SAVEPOINT` around the statement
it expects to fail. For example, the re-read in `ensureActivePassId`
(`routes/controls.js`) or the retry in `lib/doc-versions.js` needs one when
it runs inside an outer transaction.

**Hash chains and other "read the latest row" guards rely on SQLite having
one writer at a time.** For example, the `*_chain_predecessor` triggers
compare `NEW.previous_event_hash` with `SELECT event_hash ... ORDER BY id DESC
LIMIT 1`. Under PostgreSQL's default READ COMMITTED isolation, two concurrent
transactions can both see the same latest event and both append to it,
forking the chain. Nothing in the schema stops that (there is no unique
constraint on the predecessor hash). The port must serialise each chain's
writers: `SELECT ... FOR UPDATE` on the parent row (module, connector,
condition, draft, relationship), a transaction-scoped advisory lock keyed on
the chain, or SERIALIZABLE with retry. The same applies to the
`row_version = OLD.row_version + 1` guards when the app reads a version and
then writes.

## 6. Full-text search (`search_index`)

The FTS5 virtual table becomes an ordinary table with the same five columns
and a stored generated column:

```sql
search_vector tsvector GENERATED ALWAYS AS (
  to_tsvector('simple'::regconfig,
    regexp_replace(coalesce(title, '') || ' ' || coalesce(body, ''), '[[:punct:]]', ' ', 'g'))
) STORED
```

It has a GIN index on `search_vector`, plus a b-tree on
`(workspace_id, entity_type, entity_id)` for the delete-and-reinsert that
`lib/fts.js` runs on every write. Inserts and deletes in `lib/fts.js` work
unchanged.

Punctuation is turned into spaces before parsing so that control references
tokenize as FTS5's `unicode61` tokenizer splits them. PostgreSQL's own
parser would keep `A.5.18` as one token, and a search for `A.5` would find
nothing. `'simple'` lower-cases and does not stem, like `unicode61`. Unlike
`unicode61`, it keeps diacritics (`café` does not match `cafe`; the
`unaccent` extension would fix that), and in a `C` database only ASCII
letters are lower-cased.

On the copied test data (370 indexed entities), ten searches returned
exactly the same entity sets from FTS5 and from the PostgreSQL query below:
`access contr`, `risk`, `polic`, `supplier review`, `encrypt`, `A.5`,
`incident respon`, `back-up`, `ISMS`, `organisation's`.

The search query in `lib/fts.js` changes from

```sql
SELECT entity_type, entity_id, title, snippet(search_index, 4, '<<', '>>', '…', 12) AS excerpt,
       bm25(search_index) AS score
  FROM search_index WHERE workspace_id=? AND search_index MATCH ?
 ORDER BY score LIMIT ?
```

to

```sql
SELECT entity_type, entity_id, title,
       ts_headline('simple', body, q, 'StartSel=<<, StopSel=>>, MaxWords=12, MinWords=4, MaxFragments=1') AS excerpt,
       ts_rank(search_vector, q) AS score
  FROM search_index, to_tsquery('simple', $2) AS q
 WHERE workspace_id = $1 AND search_vector @@ q
 ORDER BY score DESC
 LIMIT $3
```

with the match expression built as a tsquery instead of FTS5 syntax. Each
user term becomes a prefix match and terms are ANDed, as today:

```js
const tsquery = String(query).split(/\s+/)
  .map(t => t.split(/[^\p{L}\p{N}]+/u).filter(Boolean))   // "o'brien" -> ["o", "brien"]
  .filter(parts => parts.length)
  .map(parts => '(' + parts.map((p, i) => (i === parts.length - 1 ? `${p}:*` : p)).join(' <-> ') + ')')
  .join(' & ');
```

Behaviour differences to accept or handle:

- **Score direction flips:** bm25 is lower-is-better (`ORDER BY score` ascending);
  `ts_rank` is higher-is-better (`ORDER BY score DESC`). The numbers are on
  different scales.
- `ts_headline` does not add `…` at fragment edges as `snippet()` does; add
  it in JavaScript if the UI relies on it. It parses the original `body`, so
  a hit inside a punctuated token such as `A.5.18` is found but not
  highlighted.

## 7. Copying a SQLite database: `scripts/sqlite-to-postgres.js`

```sh
node scripts/sqlite-to-postgres.js --sqlite data/iso27001.db --pg postgres://user:pass@host:5432/isms
```

Stop the app first, or copy from a backup. In one transaction, the tool:

1. applies `migrations/postgres/baseline.sql`, unless `--no-schema` is given;
2. refuses to load into tables that already hold rows, unless `--truncate`;
3. sets `session_replication_role = replica` for the transaction. This turns
   off the guard triggers and foreign-key checks during the load, so
   historical rows load as they are: an approval by a since-deactivated user
   would otherwise fail the actor triggers, and the reference cycles have no
   valid insert order. It needs a superuser, or on PostgreSQL 15+
   `GRANT SET ON PARAMETER session_replication_role TO <role>`. CHECK, NOT
   NULL and UNIQUE are still enforced;
4. copies every table parent-first, keeping ids. Values are converted to the
   target column type, and anything that does not fit fails, naming table,
   column and row: text in an integer column, a NUL character in text, a
   number in a blob column. Integers are read as BigInt, so 64-bit values
   are exact. Integers in `DATE`/`DATETIME` columns are possible because of
   SQLite's NUMERIC affinity; they are copied as their decimal text and
   reported as a note;
5. sets every identity sequence past both the highest copied id and SQLite's
   `sqlite_sequence` value, so ids deleted under AUTOINCREMENT are never
   reused;
6. prints SQLite and PostgreSQL row counts for every table, re-checks every
   foreign key for orphans, and commits only if all counts match and there
   are no conversion errors or orphans. Otherwise it rolls back (the target
   is left unchanged) and exits 1. Setup problems exit 2.

FTS5 shadow tables and `sqlite_sequence` are not copied; the `search_index`
rows are. The `sessions` table that the old SQLite session store
(`better-sqlite3-session-store`) created at runtime is skipped with a message:
the PostgreSQL session store (`lib/pg/session-store.js`) keeps sessions in its
own table, and users sign in again after the move. Encrypted field values are
copied as stored, so the deployment must keep the same `ISMS_KEY_FILE` (or
`ISMS_MASTER_KEY`).

The tool reads the SQLite file through `better-sqlite3`, which stays in
`package.json` for this tool and the checks in `scripts/postgres/`; the
application does not load it.

  | Views | 2 | 2 | |

  | Functions | — | 63 | 4 helpers + 59 trigger functions. |

Semantic differences no grep finds:

- **NULL ordering:** SQLite sorts NULLs first in ascending order, PostgreSQL
  last. Add `NULLS FIRST` (`ASC`) or `NULLS LAST` (`DESC`) where the app
  depends on it (712 `ORDER BY` clauses in total).
- **Predicates in select lists** (`x IS NULL AS flag`, `a = b AS same`)
  return `true`/`false`, not 1/0. Cast with `::int` where the JavaScript
  compares with 1.
- **Strict typing:** `''` or `'abc'` in a `bigint` column, comparing a text
  column with a bigint column, and `CAST('abc' AS INTEGER)` all raise errors
  where SQLite coerced or returned 0.
- **GROUP BY:** SQLite accepts selected columns that are neither grouped nor
  aggregated; PostgreSQL rejects them unless the primary key is grouped.
- **Double-quoted strings:** SQLite treats `"text"` as a string when no column
  has that name; PostgreSQL always treats it as an identifier.
- **Explicit ids:** inserting an explicit id into an identity column does not
  advance its sequence. Seeders that do it must call `setval` afterwards (the
  copy tool already does).
- **Row counts:** `info.changes` → `result.rowCount`.
- `lib/dal.js`, an unused stub that switched to `pg` when `DATABASE_URL` was
  set, has been deleted. The data layer is `lib/pg/`
  (`docs/postgres-data-layer.md`).

## 10. Regenerating after the SQLite baseline changes

`migrations/postgres/baseline.sql` is generated; never edit it by hand. When
`migrations/baseline.sql` changes, regenerate it and re-run the checks in
section 8. Step 5 needs the SQLite application's `db.js` and seeder, which
this branch no longer has (`DB_PATH` is gone): run that step in a checkout of
the SQLite release (tag `handover-baseline`). Everything else runs from the
repository root, with Docker running:

```sh
# 1. Regenerate (or, with --check, only report whether the committed file is current).
node scripts/postgres/generate-baseline.js
node scripts/postgres/generate-baseline.js --check

# 2. A scratch PostgreSQL 16 with two C-locale databases (pick another port if 55491 is taken).
docker run -d --name pgport-check -e POSTGRES_PASSWORD=pgport -p 127.0.0.1:55491:5432 postgres:16.4
until docker exec pgport-check pg_isready -U postgres >/dev/null 2>&1; do sleep 1; done
for db in schema_check copy_check; do
  docker exec pgport-check createdb -U postgres --template=template0 --encoding=UTF8 --lc-collate=C --lc-ctype=C "$db"
done
PG=postgres://postgres:pgport@127.0.0.1:55491

# 3. Apply the schema twice; both runs must exit 0.
for run in 1 2; do
  docker exec -i pgport-check psql -U postgres -d schema_check -q -v ON_ERROR_STOP=1 -f - \
    < migrations/postgres/baseline.sql || echo "apply $run FAILED"
done

# 4. Compare the catalog with the SQLite schema and type-check every trigger condition.
node scripts/postgres/compare-catalog.js --pg "$PG/schema_check"

# 5. Build a seeded SQLite database the way the app does.
TMP=$(mktemp -d)
DB_PATH=$TMP/s.db ISMS_KEY_FILE=$TMP/k ISMS_DISABLE_JOBS=1 node -e "require('./db').init()"
DB_PATH=$TMP/s.db ISMS_KEY_FILE=$TMP/k ISMS_DISABLE_JOBS=1 node scripts/seed-realistic-engagements.js

# 6. Copy it into PostgreSQL, then compare every row and the trigger behaviour.
node scripts/sqlite-to-postgres.js --sqlite "$TMP/s.db" --pg "$PG/copy_check"
node scripts/postgres/compare-rows.js --sqlite "$TMP/s.db" --pg "$PG/copy_check"
node scripts/postgres/trigger-parity.js --sqlite "$TMP/s.db" --pg "$PG/copy_check"

# 7. Clean up.
docker rm -f pgport-check
rm -rf "$TMP"
```

What a passing run looks like:

| Step | Pass |
|---|---|
| 1 | A summary line, then `Wrote ...` (or `... is up to date` with `--check`; exit 1 means the committed file is stale). |
| 3 | No `FAILED` line. The second run prints `NOTICE: ... already exists, skipping` messages; that is expected. |
| 4 | `no structural differences`, exit 0. |
| 6 | `row counts match` from the copy tool, `0 table(s) differ` from `compare-rows.js`, and `N passed, 0 failed` from `trigger-parity.js`. The step labelled "known difference" passes when both databases reject the statement, whichever message they give (section 4). |

When a step fails:

- **The generator throws on a construct it does not recognise:** an
  unsupported SQLite function, type, default or trigger form. This is
  deliberate; nothing is copied through untranslated. Add the translation to
  `tx()` (expressions) or `translateTable()` (column definitions) in
  `scripts/postgres/generate-baseline.js`, record the rule in section 3, and
  regenerate. If one of the three AFTER→BEFORE triggers changes, the
  generator stops with `trigger changed, review override`; update its entry
  in `AFTER_TO_BEFORE`.
- **`compare-catalog.js` reports a difference:** fix the generator rather
  than the generated file.
- **New triggers:** they are translated automatically and type-checked by
  step 4. `trigger-parity.js` covers a fixed set of scenarios; add one for
  each new kind of trigger.
